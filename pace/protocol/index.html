## PACE — How We Work Here

This project runs on PACE: **Parallel Action, Compounding Effort.**
Apply both laws in every session.

### Law 1 — Act in Parallel
My attention is the bottleneck, not your speed. Work so I don't have to watch you.

- Front-load the questions. Before you start, restate the task, state your
  assumptions, and ask everything blocking in ONE message. After that, proceed
  on your stated assumptions rather than stopping to ask — flag them at the end.
- Plan first, then run. State the plan, then execute it end to end. Report once
  when you're done, not after every step.
- Aim to run unattended. If a task is too vague to work on for a long stretch
  without checking in, say so and propose how to split it into pieces that can.
- Never stall. If one piece is blocked, park it with a note, move to the next
  independent piece, and raise the block in your final report.
- Don't ask "what's next" — check the plan or backlog and take the next
  unblocked item.
- Verify your own work before reporting. Run it, test it, read it back.

### Law 2 — Compound Effort
The tenth task should be faster than the first. Leave the system better than you found it.

- Read the existing context first — this file, the README, the runbooks, the
  code's own conventions. Match what's there. Don't introduce a second way of
  doing something that already has a way.
- Correct the system, not the output. If you got something wrong because the
  context was missing or stale, fix the context file too, not just this answer.
- Extract what's reusable. When you solve something that will come up again,
  make it a template, a component, a helper, or a documented pattern — and say
  what you extracted.
- Prefer existing abstractions and the established design system. A new pattern
  needs a stated reason.
- Flag rot. If something in this file is stale or contradicts the code, say so.

### Every substantial task ends with
1. What changed
2. What you assumed
3. What's still open or blocked
4. What you'd add to the context files so the next run is faster

What changes

Four things that happen on a normal Tuesday, before and after.

  • Before — eleven minutes into a refactor it stops to ask whether to use the existing formatDate helper or add a new one.

    After — it uses the helper that's already there, says which one in the report, and doesn't interrupt.

  • Before — three clarifying questions arrive as three separate messages, each one idle until you happen to look at the terminal.

    After — all three arrive in the first message. You answer once, and it runs to the end.

  • Before — a migration fails, the run stops there, and the four unrelated tasks behind it are untouched an hour later.

    After — the migration gets parked with a note, the other four ship, and the block is the third line of the final report.

  • Before — you correct the same naming convention every week, and the correction dies with the session.

    After — the first correction gets written into the context file, and next week's run starts already knowing it.

## PACE
Act in Parallel: ask everything blocking up front in one message, then run
unattended on stated assumptions. Plan first, execute end to end, report once.
If blocked, park it and move to the next independent piece — never stall.

Compound Effort: read existing context and match it. When something's wrong
because context was missing, fix the context, not just the output. Extract
anything reusable. End with: what changed, what you assumed, what's open, and
what to add to the context files.
